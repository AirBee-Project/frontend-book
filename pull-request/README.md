# 良いPull Requestについて学ぶ

## コードレビューの文化を馬鹿にしてはいけない
コードは書かれるのは1度だが、それを読んだり利用する回数はとても多い。コードのリーダビリティは組織のスケーラビリティ、快適な開発者体験に大きな影響を及ぼす。また、他人のコードの書き方から学ぶことが多い。組織の上下関係に関係なくPRを送りあう文化があることが大切である。30分のコードレビューと修正には、今後のバグを取り除き、理論上そのコードを使いづづける限り、その恩恵を受けることが可能となる。

巨大なリポジトリへの変更は、巨大な水槽に少しの新しい液体を混ぜる行為と似ている。もし新しい液体に毒が含まれていて、誤って混ぜて（merge）してしまった場合に、その影響範囲を特定して後からバグを修正するのは至難の業である。これは巨大なコードであればあるほどそうだ。

## なぜ`Merge Request`ではないのか
Gitは本来「分散型バージョン管理システム」である。中央のサーバーに直接変更を押し込むのではなく、「私が作業したリポジトリ（またはブランチ）の変更を、あなたのリポジトリに引っ張って（Pullして）取り込んでほしい」とお願いする意味でPull Requestとなっている。

## AI開発時代のリポジトリ原則
「リポジトリを見ればすべてがわかるようにする」ことが大切である。背景にある文脈（なぜその変更が必要だったのか、どのような議論があったのか）がPRのディスクリプションやコミットメッセージにテキストとして残っていることで、AI（GitHub Copilotなど）がコードの意図を正確に読み取り、より高度なサジェストや自動レビューを行えるようになる。暗黙知をなくし、すべてのコンテキストを言語化してリポジトリ上に残すことが重要である。

## PRはコード提出者とレビュアーの共同作業である。
PRは「コードの採点」や「粗探し」の場ではない。提出されたコードをより良くし、システム全体の品質を高めるための「チームとしての対話」である。提出者とレビュアーは敵対する関係ではなく、共通のゴールに向かって協力するパートナーであることを忘れてはいけない。

# コードを提出する側
- 小さなPRを出す。複数の変更を同じPRに出さないことが基本。（依存関係があってやむを得ない場合はOK）
- 可能な限りコンフリクトを避ける。
- 関係のないファイルはCommitしない。
- タイトルと説明はわかりやすく。なぜこのPRが必要なのか、何を変更したのか。

## GitHubにおけるPRの手順

### 1. `main`からブランチを切る
1. ローカルの`main`ブランチを最新の状態にする。
```bash
git checkout main
git pull origin main
```
2. 作業用の新しいブランチを作成し、移動する。（例: `feature/add-login-button` など、作業内容がわかるブランチ名にする）

```bash
git checkout -b feature/branch-name
```

### 2. ファイルの変更を行う
1. エディタでコードを編集し、機能追加やバグ修正を行う。
2. 変更したファイルをステージング（追加）する。
```bash
git add <ファイル名>  # または git add . ですべて追加
```
3. 変更内容をわかりやすくコミットする。
```bash
git commit -m "feat: ログインボタンのUIを追加"
```
4. リモートリポジトリ（GitHub）にブランチをプッシュする。
```bash
git push origin feature/〇〇
```

### 3. GitHub上でmainへのPRを出す
GitHubのリポジトリ画面を開くと、「Compare & pull request」という緑色のボタンが表示されるのでクリックする。
- **タイトルをつける:** 「何をしたのか」が一目でわかるように書く。（例: `feat: ログインボタンの追加`）
- **どのようなPRなのか、簡潔に書く:** テンプレートがあればそれに従い、「なぜこの変更が必要か」「どうやって動作確認すればいいか」「関連するIssue番号」などを記載する。
- **レビューアーを指定する:** 右側の「Reviewers」メニューから、レビューをお願いしたいチームメンバーを選択する。

### 4. レビュアーのコメントに対処する
1. レビュアーから修正依頼（Request changes）や質問があった場合は、真摯に対応する。
2. 修正が必要な場合は、ローカルの**同じブランチ**でコードを修正し、再度 `git add` -> `git commit` -> `git push` を行う。（PRの画面には自動的に最新のコミットが反映される）
3. 対応が完了したらコメントに返信し、必要に応じて再レビューを依頼する。

# コードをレビューする側
- 敬意を持って、丁寧にレビューする。
- 変更を求める点は明確に明示する。（「マージ必須の条件」か「単なる提案」かを分ける）
- 変更の意図が分からないものは素直に質問する。
- 常に、理屈に基づいてPRを行う。理屈が不足している場合は言語化する。

## GitHubにおける手順
1. **PRの概要を確認する:** GitHub上で該当のPRを開き、「Conversation」タブでタイトルと説明を読んで、変更の目的と背景を理解する。
2. **差分を確認する:** 「Files changed」タブを開き、実際に変更されたコードを確認する。
3. **インラインコメントを残す:**
- 気になる箇所や修正が必要な箇所があれば、該当行の横にある `+` ボタンをクリックしてコメントを書く。
- 良いコードには「LGTM!（Looks Good To Me）」や「ここ綺麗でいいですね」とポジティブなフィードバックも積極的に残す。
4. **レビューを完了する:** 右上の「Review changes」ボタンを押し、以下から結論を選択して送信（Submit review）する。
- **Comment:** 承認や拒否を伴わない、一般的なフィードバックや質問。
- **Approve:** コードに問題がなく、マージして良いと承認する場合。
- **Request changes:** マージする前に、必ず修正してほしい箇所がある場合。


# PR全体のシステム自動化
- AIを使ったレビューを取り入れる。AIのチェックをクリアした後は人間がチェックする。
- GitHub Actionsを用いてLinter（構文チェック）や自動テストを実行し、テストが通らないとマージできないようにする。
- Git Hook（`Husky` や `lint-staged` など）を用いて、Commit時にformat（コード整形）やlintを強制する。
