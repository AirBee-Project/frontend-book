# 良いPull Requestについて学ぶ

## コードレビューの文化を馬鹿にしてはいけない
コードは書かれるのは1度だか、それを読んだり利用する回数はとても多い。コードのリーダビリティは組織のスケーラビリティ、快適な開発者体験に大きな影響を及ぼす。また、他人のコードの書き方から学ぶことが多い。これは組織の上下関係に関係なくPRを送りあう文化があることが大切である。30分のコードレビューと修正には、今後のバグを取り除く

## AI開発時代のリポジトリ原則
「リポジトリを見ればすべてがわかるようにする」ことが大切である。

## PRはコード提出者とレビュアーの共同作業である。

# コードを提出する側
- 小さなPRを出す。複数の変更を同じPRに出さないことが基本。（依存関係があってやむを得ない場合はOK）
- 可能な限りコンフリクトを避ける。
- 関係のないファイルはCommitしない。
- タイトルと説明はわかりやすく。なぜこのPRが必要なのか、何を変更したのか。

## GitHubにおけるPRの手順

### 1.`main`からブランチを切る

### 2.ファイルの変更を行う

### 3.GitHub上でmainへのPRを出す
- タイトルをつける
- どのようなPRなのか、簡潔に書く
- レビューアーを指定する。

### 4.レビュアーのコメントに対処する

# コードをレビューする側
- 敬意を持って、丁寧にレビューする。
- 変更点を求める点は明確に明示する。
- 変更の意図が分からないものは素直に質問する。
- 常に、理屈に基づいてPRを行う。理屈が不足している場合は言語化する。

# PR全体のシステム自動化
- AIを使ったレビューを取り入れる。AIのチェックをクリアした後は人間がチェックする。
- GitHub Actionを用いてLinterを実行する。
- Git Hookなどを用いてCommit時にformatやlintを強制する
